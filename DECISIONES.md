> Usé `BigDecimal` porque los tipos flotantes de punto aproximado como `double` o `float` pueden introducir errores de redondeo acumulativos indeseables en operaciones financieras y de cálculo monetario. ## Fase 3 — Modelo inmutable y lógica funcional

**3.1** ¿Por qué tienes **dos** clases (`ProductoEntity` y `Producto`) en lugar de una?
¿Qué te impide hacer inmutable directamente la entidad de Hibernate?

> Tenemos dos clases para separar la persistencia que son la infraestructura y la base de datos del modelo de dominio de negocio. Lo que nos impide hacer inmutable directamente la entidad de Hibernate (`ProductoEntity`) es que JPA/Hibernate exige cumplir con ciertas especificaciones de Java Beans, el cual nos dice que requiere un constructor por defecto sin argumentos para instanciación por reflexión, y los atributos no pueden ser `final` porque Hibernate necesita modificar los campos durante el ciclo de vida de la entidad (hidratación, proxying/lazy loading, dirty checking).

**3.2** Escribe el código exacto de **tus dos** copias defensivas e indica en qué línea
está cada una.

```java

this.correosNotificacion = new ArrayList<>(correosNotificacion);

// La segunda copia defensiva se encuentra en el método getter del archivo Producto.java, en la línea 41:

    return Collections.unmodifiableList(new ArrayList<>(correosNotificacion));
}
```

**3.3** ¿Por qué la copia defensiva **solo en el getter** no sería suficiente? Describe
el ataque concreto que quedaría abierto sobre **tu** clase.

> No sería suficiente porque si guardamos la referencia directa de la lista en el constructor, un atacante o cliente externo podría pasar una lista mutable al constructor.

> Ejemplo concreto de ataque: `List<String> listaMutable = new ArrayList<>(); listaMutable.add("mail@espe.edu.ec"); Producto p = new Producto(..., listaMutable);`

> y luego modificar externamente esa misma lista agregando o quitando correos (por ejemplo, `listaMutable.add("hacker@espe.edu.ec");`).

> Como la clase `Producto` conservaría la referencia al mismo objeto en memoria, el estado interno del producto cambiaría indirectamente sin pasar por ningún control, violando la inmutabilidad.

## Fase 4 — Servicio reactivo y aislamiento del bloqueo

**4.1** Pega tu método `obtenerProductosComercializables()` completo.

```java
public Flux<Producto> obtenerProductosComercializables() {
    return Mono.fromCallable(repository::findAll)
            .subscribeOn(Schedulers.boundedElastic())
            .flatMapMany(Flux::fromIterable)
            .map(ProductoMapper::toDominio)
            .map(ProductoFilters.A_MAYUSCULAS)
            .filter(ProductoFilters.IS_VALID)
            .doOnNext(ProductoFilters.LOG_PRODUCTO)
            .defaultIfEmpty(PRODUCTO_GENERICO);
}
```

**4.2** ¿Qué pasa **exactamente** si eliminas
`.subscribeOn(Schedulers.boundedElastic())` de ese método? Si lo probaste, indica qué
hilo aparecía en el log antes y después.

> Si se elimina `.subscribeOn(Schedulers.boundedElastic())`, la llamada bloqueante a la base de datos `repository.findAll()` se ejecutaría sobre el hilo que realiza la llamada. Esto bloquearía el hilo de Netty, impidiendo que procese otras peticiones HTTP concurrentes y arruinando el rendimiento reactivo no bloqueante de la aplicación.
>
> - **Antes (con `boundedElastic`):** La consulta SQL se ejecutaba en un hilo del pool elástico como `boundedElastic-1`.

```
Producto procesado -> id: null, nombre: QUINUA ORGANICA DE ALTURA | Thread: boundedElastic-1
Producto procesado -> id: null, nombre: QUINUA ROJA PREMIUM | Thread: boundedElastic-1
Producto procesado -> id: null, nombre: QUINUA NEGRA ANDINA | Thread: boundedElastic-1
```

> - **Después (sin `boundedElastic`):** La consulta SQL se ejecuta en el Event Loop de Netty con nombre similar a `reactor-http-nio-*`, en la prueba que realice se muestra con un hilo main que este como tal se traduciría al hilo Event Loop de Netty, lo que impediría el correcto funcionamiento de la aplicación.

```
Producto procesado -> id: null, nombre: QUINUA ORGANICA DE ALTURA | Thread: main
Producto procesado -> id: null, nombre: QUINUA ROJA PREMIUM | Thread: main
Producto procesado -> id: null, nombre: QUINUA NEGRA ANDINA | Thread: main
```

**4.3** ¿Por qué `Mono.fromCallable(...)` y no `Mono.just(repository.findAll())`?
(pista: cuándo se ejecuta cada uno)

> Porque `Mono.fromCallable(...)` difiere la ejecución del método `repository.findAll()` hasta el tiempo de suscripción. Al usarlo en combinación con `subscribeOn(Schedulers.boundedElastic())`, garantizamos que la operación bloqueante se ejecute en un hilo del pool elástico y no en el Event Loop.
> Mientras que `Mono.just(repository.findAll())` evalúa y ejecuta la consulta a la base de datos de manera inmediata durante el tiempo cuando se construye el flujo, utilizando el hilo principal y bloqueándolo inmediatamente.

**4.4** En **tu** código, ¿dónde usaste `defaultIfEmpty` y dónde `switchIfEmpty`, y por
qué no son intercambiables en esos dos lugares?

> En mi código:
>
> - Usé `defaultIfEmpty(PRODUCTO_GENERICO)` en el método `obtenerProductosComercializables()` para retornar un objeto directo `Producto` si el flujo se completa sin emitir elementos.
> - Usé `switchIfEmpty(Mono.error(...))` en el método `buscarPorId(id)` para alternar a otra señal reactiva (en este caso un `Mono.error`) cuando el producto buscado no se encuentra.
>
> No son intercambiables porque:
>
> - `defaultIfEmpty` acepta directamente un valor concreto de tipo `T`.
> - `switchIfEmpty` acepta un publicador alternativo (`Publisher<? extends T>`). Si intentamos usar `defaultIfEmpty` con `Mono.error`, emitirá el objeto Mono como si fuera un elemento exitoso. Si intentamos usar `switchIfEmpty` con `PRODUCTO_GENERICO`, el código no compilará porque este último es un objeto de dominio y no un `Publisher`.

**4.5** ¿Por qué `doOnNext` no sirve para transformar el elemento, si aparentemente
"recibe" el producto?

> `doOnNext` es un operador diseñado únicamente para ejecutar efectos secundarios (como hacer logs o métricas) y recibe un `Consumer<T>`, el cual no tiene valor de retorno. Dado que no devuelve nada, no puede transformar el flujo ni reemplazar el objeto emitido por otro. Para transformar o mapear el elemento del flujo a otro valor u objeto, es obligatorio utilizar el operador `map`.

## Fase 5 — Módulo de IA con LangChain4j

**5.1** Pega tu interfaz `AgroSmartAIService` completa.

```java
package ec.edu.espe.agrosmart.service;

import dev.langchain4j.service.UserMessage;

    @SystemMessage("""

    @UserMessage("""

**5.2** ¿Qué hace `@V("producto")` y qué pasaría si lo quitaras dejando solo el
parámetro?

> La anotación `@V("producto")` asocia explícitamente el parámetro del método con la variable de plantilla `{{producto}}` definida en el `@UserMessage`. Si se quitara la anotación y se dejara solo el parámetro `String producto`, LangChain4j intentaría resolver la variable automáticamente utilizando los nombres reales de los parámetros de compilación. Sin embargo, si el proyecto no se compila con el parámetro `-parameters` habilitado en el compilador de Java, la resolución fallaría en tiempo de ejecución al no poder mapear `{{producto}}`, generando una excepción.

**5.3** ¿En qué archivo y con qué líneas configuraste el modelo? ¿Por qué **no** hizo
falta declarar un `@Bean`?

> Configuré el modelo en el archivo `application-prod.properties` con las siguientes líneas (7 a 12):
>
> ```properties
> langchain4j.open-ai.chat-model.api-key=demo
> langchain4j.open-ai.chat-model.model-name=gpt-4o-mini
> langchain4j.open-ai.chat-model.timeout=30s
> langchain4j.open-ai.chat-model.log-requests=true
> langchain4j.open-ai.chat-model.log-responses=true
> ```
>
> No hizo falta declarar un `@Bean` porque el starter reactivo de LangChain4j para Spring Boot escanea estas propiedades bajo el prefijo `langchain4j.open-ai.chat-model` y registra automáticamente la instancia correspondiente de `ChatLanguageModel` dentro del contexto de Spring de forma transparente.

**5.4** ¿Por qué la llamada a la IA también necesita `boundedElastic`, si no es una
consulta a base de datos?

> Aunque no consulta la base de datos, la llamada al modelo de IA mediante `generarPublicidad(...)` es una operación de entrada/salida bloqueante, ya que realiza una petición de red HTTP/REST síncrona al servidor de OpenAI (o del proveedor configurado) y espera la respuesta completa de forma imperativa. En WebFlux, las operaciones de red síncronas/bloqueantes también bloquearían el Event Loop de Netty si no son aisladas, impidiendo que el servidor maneje peticiones concurrentes. Por ende, es necesario usar `.subscribeOn(Schedulers.boundedElastic())` para transferir la ejecución de dicha llamada a un pool de hilos separado.

**7.4** ¿Qué demuestra `assertNotSame` que `assertEquals` **no** demuestra en tu prueba
de copia defensiva?

> `assertEquals` comprueba la igualdad de contenido (que las dos listas contengan los mismos correos en el mismo orden). En cambio, `assertNotSame` demuestra la desigualdad de identidad (que las referencias corresponden a dos objetos totalmente diferentes en el heap de memoria). Esto es crucial para probar las copias defensivas, pues valida que el getter del dominio (`Producto.java`) está devolviendo una nueva instancia de la colección en cada llamada en lugar de retornar la referencia interna mutable de la clase.

**7.5** ¿Por qué una prueba de un `Flux` que no llama a `verifyComplete()` (o a
`verify()`) no está probando nada?

> En programación reactiva, los flujos (Publishers como `Flux` y `Mono`) son "perezosos" (lazy): nada ocurre hasta que exista una suscripción (`nothing happens until you subscribe`). El constructor `StepVerifier.create(flujo)` solo configura la verificación, pero no se suscribe. Invocar métodos terminales como `verify()`, `verifyComplete()` o `verifyError()` es indispensable para disparar la suscripción, obligando al flujo a emitir los elementos y ejecutar las aserciones declaradas en la prueba. Sin esto, la prueba pasará exitosamente sin haber ejecutado una sola línea del flujo.
